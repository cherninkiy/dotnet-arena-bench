# Итог PoC: arena в .NET — что решили

> Сводный документ по двум PoC. Детали и таблицы: [PoC-1: сериализация](poc-1-serialization.md),
> [PoC-2: аллокатор](poc-2-allocator.md); план и критерии — [concept.md](concept.md).

**Статус: предварительные решения.** Оба прогона сняты `--job short` на рабочей
машине (не на выделенной тишине), поэтому числа — порядок величин и отбор
гипотез. Направление выводов устойчиво (различия кратные), точные проценты —
после полного прогона.

## 1. Два вопроса — два ответа

| Вопрос | Ответ | Основание |
|---|---|---|
| Как читать бинарные структуры в hot path? | Span-based, не `BinaryReader` | PoC-1: 2.5–8× на T2, 11× на кадрах T1 |
| Даёт ли align 64 выигрыш? | На sequential-чтении — нет | PoC-1: 1 787/1 873/1 792 ns при реально разных адресах |
| Нужна ли arena для сериализации? | Нет | PoC-1: паритет с `byte[]`, проигрыш на мосту в BCL |
| Нужна ли arena как аллокатор? | **Да, для партий и scoped-владения** | PoC-2: 0.13–0.29× против пулов, B&B 1.4–3.2× |
| Выигрывает ли arena на границах (P/Invoke)? | По ns/op — нет, паритет | PoC-2 I-серия: 0.92–1.04×; вопрос уходит в GC (B-001/B-002) |
| Per-type арены вместо одной? | Да | PoC-2 M-серия: 1.48×, на перекосе 2.27× |
| Арена вместо `int[]` для CSR? | Нет | PoC-2 E01: 1.00–1.01× |

## 2. Как читать эти числа

- Оба прогона — `--job short` (3 warmup + 3 итерации) на одной машине
  (AMD Ryzen 7 4800H, Windows 10, .NET 10.0.11). Фон и турбо-частоты не
  контролировались.
- `Allocated` — только managed-куча. У арены и `NativeMemory` он **всегда 0** по
  определению диагносера, а не потому что памяти нет; RSS не собирался.
- Не измерялись и остались в [backlog](backlog.md): GC pause (B-001), pinning
  time (B-002), PMU cache/branch (B-003), contention (B-004), ARM64 (B-005),
  persistent arena (B-006).
- Сравнивать числа между разными нагрузками (например, M01 и M03) нельзя: у них
  разный объём обрабатываемых байт.

## 3. PoC-1: сериализация — коротко

Замеры на 16-байтовой записи, «быстрее» — относительно `BinaryReader` +
`MemoryStream`:

| Способ | Отношение | Комментарий |
|---|---|---|
| `MemoryMarshal.Cast<T>` | **0.12×** (8× быстрее) | лучший результат матрицы |
| `Unsafe.ReadUnaligned<T>` | 0.35× (2.9×) | без промежуточной копии |
| `MemoryMarshal.Read<T>` | 0.37× (2.7×) | одна копия структуры |
| `BinaryPrimitives` (поля) | 0.40× (2.5×) | гипотеза «10–20×» не подтвердилась |
| `BinaryReader` + FileStream | 0.39× от baseline | то есть в 2.5 раза медленнее |
| `BinaryReader` + loopback NetworkStream | 0.007× | доминирует `Send`, а не чтение |
| Кадры T1 (span + carry) | 11× быстрее | переменная длина почти не мешает |

Что решили:

- **Читать span-ом**: `Cast<T>` для однородных массивов, `Unsafe.ReadUnaligned<T>`
  для отдельных записей, `BinaryReader` — только вне hot path.
- **Арена под парсинг не нужна**: те же стратегии над ареной и над `byte[]` дают
  паритет ±10 %, а мост в BCL (`UnmanagedMemoryStream` + `BinaryReader`) дороже
  одной копии в pooled-массив.
- **Alignment не «бесплатная» оптимизация**: на sequential-чтении эффекта нет,
  значит align 64 берётся только там, где он измерен (кэш-линия, SIMD, PMU).
- **Текст и JSON — не сценарий арены**: `Utf8JsonWriter` + `ArrayBufferWriter`
  дают те же числа с нулём аллокаций.

## 4. PoC-2: аллокатор — коротко

| Кейс | Результат |
|---|---|
| Один rent/free (A01) | арена 3.1–3.4 ns **независимо от размера**; `ArrayPool` 12 ns; `NativeMemory` 58 ns…5.4 µs; `new byte[]` до 25 µs и 333 Gen2 на 1 MiB |
| Партия + `Reset` (A02) | 0.13–0.22× против `PathPool`, 1.5–4.7× против `ArrayPool` |
| Много мелких записей (A03) | арена в 12–33 раза дешевле пула; N бампов ≈ один блок |
| Обнуление (A04) | `Clear` стоит как `memset` (0.53 µs на 64 KiB); бесплатным не бывает |
| Доступ `Span`/`Memory` (B01/B02) | паритет с `byte[]`; на мелких размерах `Memory<T>` дороже доступа (11.6× на 32 B) |
| AoS против SoA (B03) | арена не влияет (1.00×), раскладка влияет в 5 раз (AoS быстрее при полном обходе) |
| CSR обход/сборка (E01/E02) | 1.00–1.01× на обходе; сборка в арене выигрывает только если массивов ещё нет |
| B&B rollback (E03) | арена в 1.4–3.2 раза быстрее `PathPool`, `ArrayPool` посередине |
| Параллельный B&B (E04) | thread-local 73 µs против shared+`lock` 304 µs (4.2×) и `PathPool` 483 µs; `ArrayPool` 89 µs |
| Incremental solve (E05) | арены 0.48–0.84× против пулов; `Reset` и пересоздание неразличимы |
| Границы (I01–I07) | арена ≈ pinned `byte[]` (0.92–1.04×) — выигрыша по ns/op нет |
| Обёртка `LibraryImport` (I09) | 1–1.6 ns на вызов, видно только на мелких payload'ах |
| mmap (I08) | арена поверх mapping ≡ арена поверх native (0.64×), BCL-аксессор в 3.8–18.9× дороже |
| Mixed workload (M01–M04) | per-type арены: 1.48× на balanced, 2.27× на skew |

## 5. Сводная таблица решений для netgraph-optimizer

| Точка | Сейчас | Решение | Основание |
|---|---|---|---|
| Чтение T2 в hot path | `BinaryReader` / ручное | `MemoryMarshal.Cast<T>` для массивов, `Unsafe.ReadUnaligned<T>` для отдельных записей | PoC-1: 2.5–8× |
| Кадры T1 | `BinaryReader` | Span + carry-буфер | PoC-1: 11× |
| Текст и JSON | `Utf8JsonWriter` | оставить как есть | PoC-1: паритет, 0 alloc |
| Хранение CSR | `int[]` | оставить `int[]` | PoC-2 E01: паритет |
| `PathPool` (пути, scratch узла) | `ConcurrentBag<int[]>` | арена + `Mark`/`Release` | PoC-2 E03: 1.4–3.2×, пик — один буфер |
| Scratch на итерацию/запрос | пул | арена + `Reset` | PoC-2 A02: 0.13–0.22× |
| Параллельный поиск | — | thread-local арена (или `ArrayPool` на поток) | E04: 4.2× против замка, 1.2× против `ArrayPool` |
| Границы P/Invoke | pinned `T[]` | пока **не менять** | паритет по ns/op; сначала B-001/B-002 |
| Shared memory / IPC | — | арена поверх `MemoryMappedViewAccessor` | I08: 3.8–18.9× против аксессора |
| Commodity-типы (mixed) | общая память/пул | per-type арены | M: 1.48–2.27× |
| Раскладка записей | — | AoS, если обход читает все поля; SoA — только для подмножества | B03: 5× в пользу AoS при полном обходе |
| `Memory<T>` на мелких payload | — | `Span<T>` | B02: 11.6× на 32 B |

## 6. Отрицательные результаты (что не подтвердилось)

Это не менее важная часть итога: каждая строка — идея, которую **не** надо
тащить в продукт, с указанием, чем она проверена.

| Идея | Что измерено | Вывод |
|---|---|---|
| align 64 ускоряет чтение | PoC-1 S10/S11/S12: 1 787 / 1 873 / 1 792 ns при реально разных адресах | эффекта нет на sequential-обходе; нужен PMU-прогон (B-003) |
| arena ускоряет сериализацию | PoC-1: паритет с `byte[]` ±10 %, мост в BCL дороже копии | арена для парсинга не нужна |
| arena ≫ pinned `T[]` на P/Invoke | PoC-2 I01/I02/I06/I07: 0.92–1.04× | `fixed` над существующим массивом практически бесплатен |
| arena ≫ копия в native callback | PoC-2 I04/I05: 0.99–1.05×, на 64 KiB арена на 17 % медленнее | выигрыша нет; разрыв на 64 KiB — открытый вопрос (B-003) |
| arena вместо `int[]` для CSR | PoC-2 E01: 1.00–1.01× | `int[]` уже zero-alloc |
| «Span-based в 10–30 раз быстрее» | PoC-1: 2.5–8× | гипотезы были завышены в 2–3 раза |
| `Reset` как отдельная оптимизация | PoC-2 E05: пересоздание блока не дороже `Reset` | важен отказ от аллокации, а не сам откат |
| Managed-обёртка `LibraryImport` дорогая | PoC-2 I09: 1–1.6 ns на вызов | оптимизировать нечего; важно только на мелких payload'ах |
| SoA быстрее AoS | PoC-2 B03: SoA в 5 раз медленнее при обходе, читающем все поля | SoA — только для подмножества полей |
| `Memory<T>` дешевле `Span<T>` по гибкости | PoC-2 B02: на 32 B дороже в 11.6× | `Span` везде, где хватает `ref struct` |

## 7. Порядок внедрения (если решение — тащить арену)

1. **Span-based чтение T2/T1** — самый дешёвый шаг: не требует арены вообще,
   даёт 2.5–11× и проверяется существующими тестами форматов.
2. **B&B scratch: арена + `Mark`/`Release`** вместо `PathPool` — 1.4–3.2× и
   пиковая память в один буфер. Требует принять контракт ADR-001 D9
   (инвалидация `Span`/`IntPtr` после отката) и бюджет размера блока.
3. **Партии на итерацию + `Reset`** — 0.13–0.22× на партиях, тот же контракт D9,
   но без вложенных scope.
4. **Thread-local арена** для параллельного поиска — 4.2× против shared+`lock`;
   если достаточно одного буфера на поток, `ArrayPool` даёт почти то же (1.2×
   разницы), поэтому шаг опционален.
5. **Границы и mmap** — только после B-001/B-002 (GC pause, pinning time) и
   B-003 (PMU): по ns/op там выигрыша нет, аргумент — GC-давление и отсутствие
   pinning'а, а это надо измерить прежде, чем менять код на границе.

## 8. Что осталось

- **R01–R04** (`SourcesBench`) — единственная нереализованная серия PoC-1: цена
  `Stream.Read` без парсинга. Сейчас видно, что `S03` доминируется `Send` в
  loopback, но отделить источник от парсера нечем.
- **Полный `--job default`** на выделенной машине для финальных таблиц обоих
  отчётов + RSS/working set (`dotnet-counters`).
- **`docs/methodology.md`**: как воспроизводить, как читать отчёты, ограничения
  (пока это §3 обоих отчётов).
- **Backlog** ([backlog.md](backlog.md)): B-001 (GC pause), B-002 (pinning time),
  B-003 (PMU), B-004 (contention), B-005 (ARM64), B-006 (persistent arena). Первые
  три решают, остаются ли открытыми границы и alignment; B-004 даёт цифры к E04.
- **Открытые вопросы измерения из PoC-1 §11**: устойчивость разрыва `S09`/`S15`
  (GC-куча против unmanaged-страницы) и знак BE/LE на паре `S11`/`S19` — оба
  меньше разрешения `--job short`.
