# PoC-1: Serialization — результаты

> Вопрос PoC-1 ([concept.md](concept.md), 5.1): какой способ
> сериализации/десериализации быстрее и экономнее на интеграциях, и даёт ли
> arena выигрыш?

**Статус: основные числа — стенд A (final), повторный прогон — стенд B
(provisional replication).** Таблицы ниже сняты с одного полного прогона
`--job default` на стенде A: выделенная машина, Windows 11, AMD Ryzen 7 7800X3D,
.NET 10.0.13 (окружение и лог — в
[`results/stand-a-2026-10-22-win11-7800x3d`](../results/stand-a-2026-10-22-win11-7800x3d/MANIFEST.md)).
На стенде B ([Ubuntu 24.04.5, Ryzen 7 4800H](../results/stand-b-2026-10-24-linux-4800h/MANIFEST.md))
матрица снята дважды; он проверяет **отношения**, но не заменяет абсолютные
числа A. Причины: другой CPU/ОС/JIT-архитектура, governor `schedutil` и
неподнятый high priority. Медиана расхождения абсолютных значений между
стендами — 54 %, поэтому смешивать их нельзя. Выводы ограничены этими форматами,
размерами и машинами; на быстрых кейсах см. оговорки о разбросе в §4. Это не
оценка выигрыша на всей production-нагрузке.

## 1. Что измерялось

Матрица из [concept.md](concept.md) 5.1, три семейства:

| Семейство | Формат | Диапазон | Что сравнивается |
|---|---|---|---|
| **T2** (`S01`–`S22`) | fixed-layout records 16/32/64/128/256 B | `S01`–`S09` — потоки и span, `S10`–`S20` — arena, `S21`/`S22` — variable-length | способ чтения и память под ним |
| **T1** (`V01`–`V08`) | variable-length frames (8 B header + 16..128 B payload) | 256 кадров (~20 KiB) | BinaryReader / Span / Unsafe / Pipelines / arena / carry |
| **T3** (`C01`–`C10`) | text (CSV-строки) и JSON | 512 строк / 64 сообщения | span-парсинг, Utf8JsonReader/Writer, JsonSerializer, ручная запись |

Общие свойства прогона:

- **Генерация данных детерминированная, без RNG**: каждый формат задаёт
  `Create(index)` — фиксированные формулы (seed 42 из README здесь не нужен,
  случайности нет вообще). Один и тот же образ читают все стратегии.
- **Проверка корректности — отпечаток**: каждая стратегия возвращает сумму
  отпечатков записей/кадров/сообщений, поэтому (а) числа сравнимы,
  (б) JIT не выбрасывает чтения как мёртвый код, (в) расхождение в смещениях,
  порядке полей или байт-порядке видно сразу. Инвариант закреплён тестами
  (`ArenaBench.Serialization.Tests`).
- **Арена** — `ArenaBench.Core` (ADR-001), выравнивание задаётся на аллокацию
  (`AllocPtr(size, align)`): `S10/S11/S12` читают одну и ту же нагрузку при
  align 1/16/64.
- **Alignment материализуется по-настоящему.** Блок арены выровнен на 64 B, а
  первая bump-аллокация попадает на offset 0, поэтому при любом `align` указатель
  оказался бы одним и тем же. Payload поэтому всегда стоит за однобайтовым probe:
  offset 1 (реально невыровнено), 16 и 64. Тесты фиксируют `ptr % 64 = 1/16/0` и
  три различных адреса — без этого ось «tight/16/64» измеряла один и тот же
  layout (первая версия именно так и делала, см. 2).
- **`Allocated`** — управляемые байты от `MemoryDiagnoser`. Для arena и
  `NativeMemory` он равен нулю **по определению** (unmanaged-память диагносер не
  видит), RSS в этом прогоне не собирался ([concept.md](concept.md) 7.1).

## 3. Как воспроизвести

```bash
# Сборка и тесты
dotnet build -c Release
dotnet test -c Release

# Один класс из матрицы (пример: 16 B ladder, S01-S20)
dotnet run -c Release --project benchmarks/ArenaBench.Serialization.Bench \
  -- --filter *T2ServiceRecord16Bench* --job default

# T1 и T3
dotnet run -c Release --project benchmarks/ArenaBench.Serialization.Bench \
  -- --filter *T1StreamBench* --job default
dotnet run -c Release --project benchmarks/ArenaBench.Serialization.Bench \
  -- --filter *T3TextBench* --job default

# Вся матрица разом (так сняты таблицы ниже)
dotnet run -c Release --project benchmarks/ArenaBench.Serialization.Bench -- --filter *
```

Отчёты каждого класса BDN складывает в
`results/stand-a-2026-10-22-win11-7800x3d/run1/serialization/results/*-report-github.md`.
Рядом лежат CSV, HTML и лог прогона; полная раскладка — в
[`results/README.md`](../results/README.md).

### Требования к сопоставимому прогону

Числа в таблицах ниже сняты `--job default` на машине, где больше ничего не
работало; требования к такому прогону:

1. Закрыть фоновые процессы (браузер, индексаторы, обновления, анализ в IDE), не
   запускать параллельно другие бенчмарки и сборки.
2. Зафиксировать питание и частоты: Windows — схема «Высокая производительность»
   (BDN переключает её сам) и выключенный Turbo Boost; Linux —
   `cpupower frequency-set -g performance` и, при желании максимальной
   стабильности, отключённый `intel_pstate` turbo.
3. Гонять серии по одной (`--filter *T2*`, `--filter *T1StreamBench*`, …), а не всё
   сразу: длинный прогон накапливает тепловой троттлинг и портит хвост таблицы.
4. Сохранять окружение из шапки отчёта BDN (CPU, JIT, SDK) вместе с числами —
   оно уже попадает в каждый `*-report-github.md`.
5. PMU-метрики (cache-misses, branch-misses) собираются **только на Linux**:
   `perf stat -e cache-misses,cache-references,branch-misses,branch-instructions dotnet run …`;
   на Windows это ETW/WPR и заметно дороже в настройке
   ([backlog](backlog.md) B-003).
6. GC pause и pinning time в этот прогон не входят — это
   [backlog](backlog.md) B-001/B-002; RSS/working set снимается отдельно
   (`dotnet-counters`).

## 4. Ограничения прогона

- `--job default` — длинный прогон: разброс по быстрым кейсам (десятки–сотни нс)
  всё ещё заметен, поэтому выводы по ним делаются по кратным различиям.
- **Стенд B не заменяет стенд A**: абсолютные значения между ними расходятся на
  ~54 % (медиана), сравнимы только отношения. На B не подтвердились величина
  накладных расходов `IBufferWriter`-моста (C04) и отношения на 128 B из-за
  выброса baseline `S01`; см. §7 и §11.
- Машина выделенная: фоновая нагрузка выключена, план питания переключает BDN.
- **Не измерялись** (вне scope, [backlog.md](backlog.md)): GC pause (B-001),
  pinning time (B-002), cache miss / branch mispredict через PMU (B-003),
  contention (B-004), ARM64 (B-005).
- Серии **R01–R04** (`SourcesBench`, чистая цена чтения источника без парсинга)
  в этот прогон не входят: они нужны, чтобы отделить цену `Stream.Read` от цены
  парсинга, и остаются на следующий шаг.

### 5.3. Наблюдения по T2

1. **Arena как память под парсинг не выигрывает.** `S05` (`byte[]`) и `S11`
   (arena align 16) различаются на ±4%, причём знак меняется от размера
   (1 131 против 1 088 ns при 16 B; 1 699 против 1 692 ns при 256 B). Оба пути
   читают линейный span, разницы в машинном коде нет — подтверждение гипотезы
   concept.md 11.3 «arena не оправдана для homogeneous bulk».
2. **Alignment не влияет на последовательный парсинг — и теперь это измерено.**
   `S10`/`S11`/`S12` действительно стоят на разных адресах (offset 1/16/64), но
   результаты совпадают: 1 075.8 / 1 087.5 / 1 073.1 ns (16 B),
   1 365.3 / 1 356.3 / 1 402.5 ns (128 B), 1 707.4 / 1 691.7 / 1 721.0 ns (256 B).
   Гипотезы «align 64 при size 64 даёт +50–100%» и «align 64 при size 16 теряет
   30–50%» не подтвердились для sequential-чтения: запись читается подряд, а на
   x64 невыровненная загрузка стоит примерно столько же, сколько выровненная.
   Проверять это надо на «случайном доступе к отдельным полям» плюс PMU-метриками
   (backlog B-003). Struct-view кейсы (`S13`–`S15`) читают align-16 блок
   намеренно — так они сравнимы с `S07`–`S09` по managed `byte[]`.
3. **Struct view быстрее полей, bulk view быстрее всех.** `S07`/`S08`/`S13`/`S14`
   (0.19–0.41×) экономят повторные чтения полей; `S09`/`S15`
   (`MemoryMarshal.Cast`, 0.11–0.14×) не делают ни копий, ни повторных смещений —
   **в 7–12 раз быстрее потока**, 1.5–4 ns на запись. На B отношение `S09/S01`
   равно 0.125–0.127 при 16 B, 0.102–0.103 при 32 B и 0.078 при 64 B, то есть
   направление и порядок сохраняются.
4. **BinaryReader — самый медленный способ чтения** (2.4–4.9× медленнее baseline
   при прочих равных): `S01`–`S04` выигрывают у span-вариантов только тогда,
   когда узкое место — сам источник (файл, сеть).
5. **UnmanagedMemoryStream как мост — дорого.** `S04`/`S17` медленнее
   MemoryStream-варианта в 2.2–2.4×, то есть «мост в BCL» чтение не ускоряет.
   При этом `S18` (скопировать арену в pooled `byte[]` и парсить span-ом)
   **в 5.6 раз быстрее** `S17` при 16 B (1 110 против 6 246 ns) и в 8.3 раза при
   256 B (2 609 против 21 758 ns): если данные нужны managed-коду, копия дешевле
   чтения через `UnmanagedMemoryStream`.
6. **Endianness-своп не виден**: `S06` и `S19` (explicit BE) в пределах ±1.5% от
   LE-вариантов (1 131.3 против 1 127.4 ns при 16 B). Гипотеза «−5–10%» не
   подтвердилась — на x64 `bswap` тонет в стоимости доступа к памяти.
7. **Zeroing дорог только на крупных записях**: `S20` (`AllocSpanZeroed` + copy) —
   0.43× от baseline при 16 B (1 192 ns, из них ~100 ns поверх `S11`) и 0.34× при
   256 B (3 163 против 1 692 ns у `S11`, то есть +87% на 64 KiB).
8. **Variable-length:** обход кадров span-ом (`S21`, 390 ns на 256 кадров) против
   BinaryReader через мост (`S22`, 6 762 ns) — та же картина, что в фиксированных
   записях.
9. **`Cast` по арене и по `byte[]` сошлись.** `S09` 378.2 ns против `S15` 380.8 ns
   при 16 B (+0.7%), 977.7 против 984.6 ns при 256 B (+0.7%), на 32 B — +5.2%
   (467 против 491 ns), на 64 B арена даже быстрее (−4.2%). Разрыв из первого
   прогона (когда до исправления оси alignment `S15` читал тот же 64-выровненный
   адрес, что и `S09`) на полном прогоне исчез: разница укладывается в разброс,
   отдельный кейс с прогревом областей не нужен. На B `S15/S09` = 1.009/1.001
   при 16 B, 1.002/0.988 при 32 B и 1.020/1.025 при 256 B — тот же паритет.

## 6. T1: variable-length frames (V01–V08)

256 кадров (8 B header + 16..128 B payload, ~20 KiB), baseline — `V01`.

| Method | Mean | Ratio | Allocated |
|---|---:|---:|---:|
| V01 MemoryStream + BinaryReader | 3 732.9 ns | 1.00 | — |
| V02 Span.Slice + BinaryPrimitives | 385.2 ns | 0.10 | — |
| V03 Span + Unsafe.ReadUnaligned | 415.0 ns | 0.11 | — |
| V04 Pipelines (PipeReader + SequenceReader) | 2 285.0 ns | 0.61 | 944 B |
| V05 Arena tight (offset 1) + primitives | 388.7 ns | 0.10 | — |
| V06 Arena align 64 + primitives | 389.9 ns | 0.10 | — |
| V07 Carry (managed buffer), 13 B за чтение | 5 825.8 ns | 1.56 | — |
| V08 Carry (arena buffer), 13 B за чтение | 5 857.4 ns | 1.57 | — |

1. **Span-обход кадров — в 9–12 раз быстрее BinaryReader** и без аллокаций
   (`V02`/`V03`/`V05`/`V06` ≈ 385–415 ns на 256 кадров ≈ 1.5 ns на кадр на A;
   на B — 487–630 ns, 1.9–2.5 ns на кадр).
2. **Pipelines работоспособен, но не бесплатен**: 2 285 ns (0.61×) и **944 B на
   вызов** — цена буферов и сегментов `PipeReader`. Для hot path без реальной
   асинхронности он проигрывает span-чтению в 6 раз (B: 0.65×, те же 944 B).
3. **Alignment на кадрах не проявляется**: `V05` 388.7 против `V06` 389.9 ns — при
   реально разных адресах (offset 1 против offset 64), тот же вывод, что в T2.
4. **Carry — самая дорогая стратегия** (A: 1.56–1.57× от baseline, 5.83–5.86 µs;
   B: 2.05–2.12×, 11.7–12.0 µs): чтение по 13 байт за раз с компактированием
   буфера стоит в 15–19 раз дороже готового буфера в памяти. Managed-буфер и
   арена дают одинаковый результат (A: 5 825.8 против 5 857.4 ns; B: 12 004
   против 11 823 ns, разница в шуме): узкое место — не аллокатор, а цена
   `Read` и логика carry.

## 7. T3: text и JSON (C01–C10)

Text-нагрузка — 512 строк, JSON-нагрузка — 64 сообщения; writer'ы измеряются на
**одном** сообщении. Baseline — `C01` (span-парсинг текста).

| Method | Mean | Ratio | Allocated |
|---|---:|---:|---:|

1. **Arena под текст/JSON не выигрывает** — ни в парсинге (`C01` против `C02`:
   +4.0%; на B +0.3/+2.1%), ни в чтении JSON (`C05` против `C06`: −0.3%, то есть
   паритет; на B `C06/C05` = 1.04–1.07). Знак разницы меняется от прогона к
   прогону, а не держится — это паритет, а не тенденция. Гипотеза concept.md 11.1
   «T3 JSON в arena ≈ ArrayBufferWriter» подтверждается: арена не даёт ни
   выигрыша, ни потери.
2. **Мост `IBufferWriter` в арену стоил ~16% только на A** (`C03` 190.9 против
   `C04` 221.4 ns). На B `C04/C03` = 0.998/1.006, то есть накладные расходы не
   воспроизвелись; аллокаций в обоих случаях 0. Устойчивого вывода о цене моста
   нет — в таблице оставлено число A, но переносить его на другую машину нельзя.
3. **Ручная запись вдвое быстрее JSON-писателя** (`C09` 87.6 против `C03`
   190.9 ns; на B 148–157 против 310–311 ns, то же ~2×), но она и делает меньше:
   без экранирования, проверок и состояния writer'а. Для известного ASCII-формата
   это оправданный путь, для произвольных данных — нет.
4. **Managed-путь разгромно проигрывает** (`C10` — 2.0× медленнее span-парсинга
   и **145 KB аллокаций** на 512 строк ≈ 284 B на строку; на B — 3.0–3.2× и те же
   145 KB). Главный отрицательный результат T3: `GetString` + `Split` — не
   вариант для hot path.
5. **`JsonSerializer` на одном сообщении дешевле ручного reader'а** в пересчёте на
   сообщение (`C07`/`C08` ≈ 0.20 µs против ≈ 0.32 µs у `C05`; на B — 0.35–0.39 µs
   против 0.56 µs), но платит аллокациями (152–272 B на вызов).
6. **JSON-чтение дороже текстового** (A: ≈ 322 ns на сообщение против ≈ 38 ns на
   строку; B: ≈ 556 ns против ≈ 47 ns): `Utf8JsonReader` проверяет структуру и
   типы, а не режет по разделителям.

## 10. Решение для netgraph-optimizer

По итогам обоих PoC картина такая:

- **Hot-path структуры читать span-ом, а не через `BinaryReader`.** Минимум
  потерь: `MemoryMarshal.Cast<T>` для однородных массивов записей и
  `Unsafe.ReadUnaligned<T>` / `MemoryMarshal.Read<T>` там, где нужен доступ к
  отдельным записям. `BinaryReader` — для кода вне hot path.
- **Арена под сериализацию ничего не добавляет**: парсинг из арены и из `byte[]`
  одинаков, а мост в BCL (`UnmanagedMemoryStream` + `BinaryReader`) дороже копии.
  Если данные уже в арене, дешевле один раз скопировать их в pooled `byte[]` и
  парсить span-ом (S18 против S17).
- **Выравнивание — не «бесплатная» оптимизация**: на sequential-чтении эффекта не
  видно, поэтому align 64 стоит брать только там, где он измерен (кэш-линия,
  SIMD, PMU — B-003).
- **Текст и JSON — не тот сценарий**: arena не нужна; `GetString`/`Split` не
  использовать; `Utf8JsonWriter` в арену допустим без потерь, но и без выигрыша.
- **Что остаётся за ареной — границы и аллокации, а не парсинг.** Это проверяет
  PoC-2: P/Invoke, native callbacks, alloc/free, B&B rollback.

## 11. Что дальше

1. **R01–R04** (`SourcesBench`): чистая цена `Stream.Read` по источникам —
   отделит «дорогой источник» от «дорогого парсинга». Сейчас видно, что `S03`
   доминируется отправкой данных в loopback на каждую итерацию, а не чтением.
2. **RSS/working set** (`dotnet-counters`) к финальным числам: отчёты дают только
   управляемые аллокации и ns/op.
3. **Остались открытые вопросы по измерению:**
   - struct view по *невыровненной* памяти: `S13`–`S15` читают align-16 блок
     намеренно, а `S10` показывает, что field-by-field от выравнивания не зависит.
     Отдельные кейсы нужны только если PMU-прогон (B-003) покажет эффект;
   - разрыв `S09`/`S15` (см. 5.3 п. 9): на полном прогоне он сошёлся (±1% при 16
     и 256 B), отдельный кейс с прогревом областей не нужен;
   - BE vs LE на паре, отличающейся *только* порядком байт (`S11`/`S19`): +4.0% в
     пользу LE, но на паре разных образов (`S05`/`S06`) знак обратный, поэтому
     вывод — паритет.
4. **Повторный прогон (стенд B) добавил два ограничения:** baseline `S01` на
   128 B нестабилен (−19 % между run1/run2), поэтому отношения `*/S01` на 128 B
   не выводятся; накладные расходы `IBufferWriter`-моста (C04) на B не
   воспроизвелись. Оба пункта внесены в §4 и §7.
