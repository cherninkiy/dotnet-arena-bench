# Методология прогонов

Документ фиксирует, **как снимаются числа**, которые попадают в
[poc-1-serialization.md](poc-1-serialization.md),
[poc-2-allocator.md](poc-2-allocator.md) и [summary.md](summary.md), и что именно
означает каждый профиль. Он не заменяет раздел «Окружение прогона» в отчётах:
там — фактические характеристики машины, здесь — требования к ней, порядок
действий и то, что по снятым числам утверждать нельзя.

## 1. Профили

| Профиль | Команда | Назначение | Что можно утверждать |
|---|---|---|---|
| smoke | `--job short` | CI, отбор гипотез | порядок величин и **кратные** различия (≥ 2×) |
| финальный | без `--job` (default) | числа для решений | различия от ~5–10 %; при двух прогонах — меньше |
| dry | `--job dry` | кейс запускается и считает | о времени — ничего, только корректность запуска |

`BenchmarkConfig` включает `MemoryDiagnoser` и `ThreadingDiagnoser` для всех
кейсов, поэтому `Allocated`, `Gen0/1/2` и `LockContentions` есть в любой таблице.
Диагностеры видят только управляемую память: у арены и `NativeMemory` `Allocated`
равен нулю **по определению**, RSS в прогон не входит (см. 4).

## 2. Чеклист машины перед финальным прогоном

- [ ] Машина не виртуалка и не shared; если это всё-таки VM — так и написать в
      отчёте (числа PoC-1/PoC-2 сняты именно на рабочей VM, см. оговорки в
      «Окружение прогона»).
- [ ] Фоновая нагрузка выключена: IDE, индексация, обновления ОС, браузер,
      сканер антивируса, Docker, синхронизация файлов.
- [ ] Питание: план «Высокая производительность», ноутбук от сети; в Linux —
      governor `performance` (`cpupower frequency-set -g performance`).
- [ ] Температура в норме, троттлинга нет; не запускать прогон сразу после
      тяжёлой задачи и не мешать прогону другой работой.
- [ ] Для параллельных кейсов (E04) зафиксировано число логических ядер
      (`start /affinity` в Windows, `taskset -c` в Linux) — иначе числа зависят
      от того, что ещё попало в процессор.
- [ ] Прогон повторён дважды (в разное время): сравниваются не только Mean, но и
      разброс между прогонами.

## 3. Команды

```bash
# Сборка и тесты (та же конфигурация Release, что у бенчей)
dotnet build -c Release
dotnet test -c Release

# Одна серия, финальный профиль (меньше шума и теплового дрейфа, чем при полном прогоне)
dotnet run -c Release --project benchmarks/ArenaBench.Allocator.Bench -- --filter "*SolverBench*" --job default --artifacts ./artifacts
dotnet run -c Release --project benchmarks/ArenaBench.Serialization.Bench -- --filter "*T2*"    --job default --artifacts ./artifacts

# Вся матрица: без --filter вход по умолчанию равен "*", см. Program.cs
dotnet run -c Release --project benchmarks/ArenaBench.Allocator.Bench    --job default --artifacts ./artifacts
dotnet run -c Release --project benchmarks/ArenaBench.Serialization.Bench --job default --artifacts ./artifacts
```

Артефакты каждого класса BDN складывает в
`<artifacts>/results/*-report-github.md` (таблицу оттуда можно вставлять в
`docs/*.md` как есть), рядом — CSV и HTML. Матрица целиком с `--job default`
идёт долго: серии снимаются по отдельности, а время первого прогона серии
используется как оценка для остальных.

## 4. Память, RSS и счётчики

- Управляемые аллокации, сборки и контеншены — из таблиц BDN
  (`Allocated`, `Gen0/1/2`, `Lock contentions`).
- Память арены — unmanaged: её не видит ни один диагностер. Для RSS нужен
  внешний инструмент:
  `dotnet-counters monitor --counters System.Runtime --process-id <pid>`
  (работает по живому процессу бенча) либо системный монитор.
- GC-паузы и pinning time — отдельные задачи ([backlog.md](backlog.md) B-001,
  B-002); в основном прогоне не собираются.
- Каждый кейс держит арену и пулы в `[GlobalSetup]`/`[GlobalCleanup]`, поэтому
  RSS в течение кейса стабилен, а «первые страницы» (page fault, zeroing от ОС)
  измеряются только в кейсах, где аллокация входит в замер (A01 NativeMemory).

## 5. Как читать таблицу BDN

- `Mean` — среднее, `StdDev` — разброс по итерациям. Если `StdDev / Mean`
  больше ~5 %, числа нельзя сравнивать на единицы процентов.
- `Ratio` считается **внутри кейса** от помеченного `[Benchmark(Baseline = true)]`,
  а не между таблицами разных серий.
- `Error`/`Median` в отчётах BDN — оценка ошибки среднего и медиана итераций;
  при малом числе итераций (`--job short`) они мало что добавляют.
- Сравнивать можно только строки одного прогона, одной машины и одного профиля.
- **Абсолютные числа E03/E05 включают подготовку солвера** (`CheapestEdge` по всем
  рёбрам, `ScratchLengthFor` по всем узлам): BDN видит кейс целиком, поэтому время
  в этих ячейках не равно чистому Rent/Release, а per-node оценки получаются
  делением на бюджет расширений (фактическое их число меньше или равно бюджету).
  Подготовка одинакова для всех вариантов внутри кейса, поэтому различия между
  вариантами сравнимы, а складывать эти числа с микрокейсами (например, A05) —
  нельзя.

## 6. Публикация чисел в docs

- [ ] Два прогона, разброс на значимых кейсах меньше 10 %.
- [ ] «Окружение прогона» заполнено из вывода BDN (пункт `// Validating benchmarks`
      и блок `Job=`).
- [ ] Рядом с таблицей указан профиль (`--job short` или default) и машина.
- [ ] Выводы сформулированы по кратным различиям, если числа сняты с `--job short`.
- [ ] Артефакты прогона сохранены (в CI — artifact, 14 дней) и названы по прогону.

## 7. Что не является финальным прогоном

- **CI** (GitHub Actions): shared-раннер, шумные соседи, виртуализация — годится
  для повторяемости и просмотра отчётов, не для чисел в выводах.
- **Рабочая машина/VM с IDE** — источник предварительных чисел; именно так
  получены таблицы PoC-1/PoC-2.
- **Полная матрица в один запуск на ноутбуке** — тепловой дрейф и троттлинг:
  серии снимаются по отдельности, между сериями даётся пауза.

## 8. Ограничения, которые методология не снимает

- Шумный сосед по гипервизору и троттлинг остаются: `--job default` повышает
  устойчивость среднего, но не изолирует машину.
- RSS, GC-паузы, pinning и PMU-метрики (cache-misses, branch-misses) требуют
  отдельных инструментов и задач (backlog B-001…B-003).
- Проверка кода кейса: числа ничего не говорят о корректности семантики — её
  держат юнит-тесты (`ArenaBench.*.Tests`), см. разделы отчётов «Инварианты».
